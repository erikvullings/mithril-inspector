## Context
User request: integrate meiosis-tracer (https://meiosis.js.org/tracer/, https://github.com/foxdonut/meiosis-tracer) as a first-class inspector plugin — its own sidenav icon and panel — without installing a separate browser extension and without changing application code.

Investigated feasibility (2026-07-19):

- meiosis-tracer's real setup is `meiosisTracer({ selector, streams: [yourStream] })`. Even though it never wraps or mutates the stream it's given, something in the host app still has to hand it a live reference to the `cell`/state stream at call time — there is no ambient way to discover an app's meiosis stream from outside. Literal reuse of the package therefore unavoidably needs at least one line of app code, which conflicts with the "no app-code changes" requirement.
- This project's own zero-app-code-change instrumentation (`packages/transform` + `packages/runtime`) only operates at the vnode/component level — it AST-transforms and monkey-patches Mithril's `m()` hyperscript and component definitions. There is no existing interception of `m.stream` anywhere in the codebase (verified via grep), so there is no existing handle on any app's reactive streams today.
- REQUIREMENTS.md §3.3 explicitly lists "time-travel debugging" and "editing attrs or state" as non-goals for the MVP, and §2.2 explicitly rules out "install a browser extension" as an instrumentation strategy. A true rewind/replay feature (calling `stream(oldValue)` to push old state back into a live app) is out of scope for now; it would require a new `m.stream`-interception subsystem plus either a manual "pick a stream" UI or fragile heuristics, and would knowingly override a documented non-goal.

Decision: scope this task to a **read-only state-history panel**, not literal meiosis-tracer integration. It captures the same signal meiosis-tracer's timeline shows (how state changed over time) by reusing infrastructure the Components tab (task 0022) already has — the attrs/state preview capture and the batched `components-updated` event — with no new low-level Mithril interception and no app-code changes. No rewind/replay of live app state.

## Acceptance Criteria
- New `OverlayTab` value (e.g. `"history"`) alongside `"components"`/`"settings"` in `packages/overlay/src/controller.ts`, with a matching sidebar icon button in `packages/overlay/src/view.ts`'s `sidebar()` (new icon added to `icons.ts`, following the existing `iconComponents`/`iconSettings` pattern).
- A new panel (new file, e.g. `packages/overlay/src/history.ts` for the store + a render function in `view.ts`) that, for the currently-selected component, shows a chronological list of state snapshots recorded after each redraw:
  - Each entry: timestamp (or relative "Nms ago"), and a compact preview of what changed (reuse `PreviewNode`/`summarizeNode` from `preview.ts`, same as the existing Attrs/State sections).
  - Selecting an entry shows a diff (added/changed/removed keys) against the previous entry — a plain JS deep-compare over the already-redacted `PreviewNode` tree is sufficient; no new serialization needed.
  - Entries are capped at a rolling buffer (e.g. last 50, configurable) to bound memory — this is the same "no unbounded growth" constraint task 0022's tree store already respects.
- Populated purely from data the runtime hook already exposes: subscribe via `OverlayHook.subscribe`, and on a `"components-updated"` event for the currently-selected component id, snapshot `hook.statePreview(id)` (and optionally `attrsPreview`) into the buffer. No new `RuntimeEvent` variants, no new protocol surface, no new runtime/transform instrumentation.
- Gated the same way the existing Attrs/State sections are (`componentTree.gating`: requires `componentTree.enabled` + mode `"full"` + `captureState`) — reuse `previewGateMessage`-style messaging when unavailable, don't invent a separate gate.
- Explicitly no write path: no button or affordance that pushes a historical value back into the app. Add a one-line doc comment noting this is deliberate (REQUIREMENTS.md §3.3).
- Works for any component's local `state`, not meiosis-specific — call out in the panel's empty-state copy that it's most useful for a root/layout component that receives the meiosis `cell().state` as its attrs/state (the common meiosis-with-mithril pattern), since that's the closest read-only analog to what meiosis-tracer shows.
- Unit tests (Vitest, beside source per CLAUDE.md) for the new store: buffer capping, diffing, event-driven capture, and reset-on-selection-change behavior (mirrors how `attrsOverrides`/`stateOverrides` already reset on selection change in `controller.ts`).
- A browser-test scenario added to the existing 0015 suite (`tests/browser`) exercising: select a component with `full` mode + `captureState` on, trigger a few state changes, open the new tab, see entries accumulate.

## Implementation Notes
- Mirror `packages/overlay/src/tree.ts`'s `ComponentTreeStore` shape for the new store (seed/apply-event/get rows), rather than inventing a different pattern.
- `OverlayController`/`OverlayViewState` in `controller.ts` will need a `history` (or similarly named) slice in `OverlayViewState`, analogous to `componentTree`, plus controller methods to select a history entry (local UI state only — no `redraw`-worthy side effects beyond that).
- Reset the buffer whenever the selection changes, same place `resetPreviewOverrides()` is already called in `controller.ts` (`handleClick`, `selectComponent`, `clearSelection`, `promoteStaleSelection`).
- If genuine time-travel (real rewind against a live app) is wanted later, treat it as a separate follow-up task — it requires a new `m.stream`-interception subsystem in `packages/runtime` (patch the stream factory, registry of created streams, a "pick a stream" UI) or a one-line opt-in registration API (`registerMeiosisStream(stream)`), either of which is materially bigger than this task and should get its own REQUIREMENTS.md scope decision first.
