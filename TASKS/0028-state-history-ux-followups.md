# 0028 State History tab: UX follow-ups from hands-on review

Status: done
Priority: medium
Owner: unassigned
Agent: claude
Area: overlay
Depends on: 0027

## Context
User feedback after using the State History tab (task 0027) against the playground's `state-demo-page.ts` (`apps/playground-vite/src/pages/state-demo-page.ts`, a closure component with `{count, label, notificationsEnabled, tasks: Task[]}` state):

1. Entries list should show newest first, not oldest first.
2. It's unclear which component's history is being shown — reuse the same left tree pane the Components tab has, kept in sync.
3. The diff panel is nearly useless for container-valued fields: changing `tasks` (an array of objects) just shows `tasks: Array(3) → Array(4)` or even `Array(4) → Array(4)` when a nested field (`task.done`) changes without the array length changing — the shallow `summarizeNode` on both sides never reveals what actually changed. Wants: expand these in the "Changes from previous snapshot" panel — a single column for the initial (added) snapshot, and for `kind: "changed"` entries whose value is an object or array specifically, a two-column before/after layout with rows aligned in the same order (diff-view style).
4. After explicitly selecting an entry, the diff panel stops following new snapshots as the app's state keeps changing — it used to auto-follow (when nothing was explicitly selected, the newest entry's diff was shown by default) but selecting anything at all — including the entry that happened to be latest at the time — permanently pins the view and never advances again.
5. Sidebar tab icons have no hover tooltip.
6. The dark-theme scrollbar look is bad (default browser scrollbar, not theme-matched).

## Acceptance Criteria
- Entries render newest-first in the `.mi-history-list`; each entry's own `#N` label still reflects its chronological recording order (`#1` = oldest), so numbering doesn't shuffle as new entries arrive — only the visual stacking order reverses.
- The History tab's `dockedPanel` body includes the same `treePane(controller, state)` on the left that the Components tab uses (`packages/overlay/src/view.ts`), so selecting a component there is visibly in sync with what's being watched. Additionally, the history panel itself shows the watched component's resolved display name in its own heading (`state.selectedComponentName`), not just an id.
- `historyStore`'s auto-follow behavior (`packages/overlay/src/history.ts`): recording a new snapshot advances the selection to the new latest entry whenever the previously-selected entry *was* the latest one at the time of recording (whether that selection came from the `null` default or from explicitly clicking the then-latest row) — pinning only survives across new snapshots when the user selected something that was **not** the latest at selection time. Unit-test both branches, including the "selected the current latest, then a new one arrives" case that was actually broken.
- `historyDiffRow` (or its replacement) in `view.ts` expands container-valued (`object`/`array` only, per the request) diff entries instead of a bare `summarizeNode(before) → summarizeNode(after))`:
  - `kind: "added"` or `"removed"` with a container value: a single-column, fully-expanded, static (non-interactive — no getter evaluation, no pagination round-trip; this is historical/frozen data, not live) rendering of that container's own entries, recursing into nested containers.
  - `kind: "changed"` with both sides containers of the same `object`/`array` kind: a two-column before/after table, rows aligned by key (object) or index (array) — before's own order first, then any keys/indices only `after` introduced — each row's two cells using the same static expanded rendering as above. Map/set/typed-array and primitive-vs-container mismatches keep the existing one-line `before → after` rendering (out of scope per the request's own "for arrays and objects only").
  - The new alignment/entries-listing logic belongs in `history.ts` (data layer, unit-testable), not inlined in `view.ts` — mirrors how `diffPreviewNodes` already lives there.
- Investigate why sidebar tab buttons' existing `title` attribute isn't producing a visible tooltip (verify empirically in a real browser via the playground, not just by reading the code — `sidebarButton()` already sets `title`/`aria-label`, so if that's not the actual gap, find what is) and fix whatever the real cause turns out to be.
- Dark-theme (and light-theme) scrollbar styling for the panel's scrollable regions (`.mi-tree-pane`, `.mi-detail-pane`, `.mi-history`, `.mi-settings`, `.mi-history-list`, etc.) via `::-webkit-scrollbar`/`scrollbar-color` using the existing `--mi-surface`/`--mi-border`/`--mi-muted` theme variables — no hardcoded colors that skip the light/dark split.
- No regressions in the existing 0027 test suite (`history.test.ts`, `controller.test.ts`, `overlay.test.ts`, `tests/browser/src/state-history.test.ts`); update any assertions that depended on the old oldest-first / shallow-diff rendering.
- Manually verified against the running playground (`apps/playground-vite`) against `state-demo-page.ts`'s task list and counter, not just unit tests, since this is a UI-feel/visual round of feedback.

## Implementation Notes
- `historyStore`'s internal entry order stays chronological (oldest-first array, `selectedDiff()`'s predecessor-lookup logic is unaffected) — only `view.ts` reverses for display.
- Reuse `isContainerNode`/`summarizeNode` from `preview.ts` for the new expanded/aligned renderers; don't duplicate PreviewNode-shape logic already in `history.ts`/`preview.ts`.
- The two-column/expanded rendering must **not** reuse `previewNodeView`/`PreviewContext` from `view.ts` as-is — that machinery's "Evaluate"/"Show more" actions round-trip through `controller.expandComponentPreview`, which always reads the *current live* selection's attrs/state, not the frozen historical snapshot being displayed; wiring a historical entry through it would silently show live data instead of the archived value. Build a small non-interactive recursive renderer instead.
