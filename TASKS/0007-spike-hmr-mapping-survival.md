## Context
Phase 0 spike 6 (REQUIREMENTS.md §21). When Vite HMR replaces a module, module/source registrations become stale. The inspector must invalidate module metadata, register replacement source records, preserve UI selection when possible, and never permanently corrupt the registry (§11.2 `handleHotUpdate`, MVP acceptance §20.1.11).

## Acceptance Criteria
- Prototype in a minimal Vite + Mithril app: edit a component file, HMR fires, and after the update hovering the re-rendered element resolves to the NEW line numbers.
- Stale source registrations for the replaced module are removed (no unbounded registry growth across repeated edits).
- A selected element/component survives the update when its identity is recoverable, or degrades to a documented "stale" state — never a crash.
- ADR written describing the invalidation/re-registration protocol between plugin (`handleHotUpdate`) and runtime.

## Implementation Notes
- Module IDs (`m:<string>`, §7.2) should be stable per file path so re-registration can replace rather than append.
- Findings feed directly into 0013 (Vite plugin `handleHotUpdate`).

- 2026-07-15 claude-opus: Built the spike as a private workspace package at `tests/fixtures/spikes/hmr-mapping-survival/`. Decides the invalidation/re-registration protocol (ADR-106) between the plugin's `handleHotUpdate` and the runtime source registry. `createRuntimeRegistry()` (`src/hmr.ts`) is keyed by a **stable-per-file module id** (`m:<string>`, §7.2) whose source table is **replaced wholesale** on re-registration — this is what bounds the registry and drops stale ids. Two-step protocol: `invalidateModule(moduleId)` (called from `handleHotUpdate` before the replacement module runs) drops the module's sources but keeps a tombstone (generation, file) so `resolveSource` returns `null` in the window → "Source file was replaced during HMR" (§16), and is the terminal state if the file is deleted; `registerModule(moduleId, registration)` (the transform's re-executed `registerModule("m:…", {…})` call, §6.1) installs the fresh source `Map`, discarding every previous id and bumping the generation. Source ids are stamped on vnodes via a `WeakMap` (§6.2, not enumerable attrs), so `sourceOf(vnode)` (hover) resolves against the *current* registry and yields the new line after re-registration. Qualified ids parse by splitting on the **last** colon (module id contains `m:`); malformed/unknown ids degrade to `null`. **Selection survival is a pure function of `(SelectionRef, live registry)` re-evaluated on read** (no eager mutation across the two steps, so it's order-independent): `select` captures an identity *signature* (component `displayName`, else element `kind`+`tagName`) but **not** line numbers; `currentSelection()` returns `live` via the stable-id tier (id still resolves + signature matches → survives a line-shift edit), `live`+`recovered` via the identity tier (unique signature match re-locates after an id shift / moved declaration), or `stale` (zero or *ambiguous* matches — refuses to guess), never a throw. Verified with **17 TDD'd tests** — `src/registry.test.ts` (14) + `src/render.test.ts` (3) — via `pnpm test` (`vitest run`) in the package: replace-not-append (dropped id → `null`); **no growth across 25 repeated edits** (`sourceCount` stays 2); the invalidate→re-register round-trip yields new lines; several **interleaved** modules stay independent across non-grouped re-registrations (no cross-module leakage, generations bump per-module); every selection tier (line-shift survive, id-shift recover, `displayName` recover, deleted→stale, module-removed→stale, ambiguous-siblings→stale). `render.test.ts` drives real `m.render` under jsdom (Mithril 2.3.8): after invalidate+re-register (article line 5→8) and a remount, hovering the re-rendered element resolves to the **new** line 8 and the stamped vnode's `.dom` is the on-screen `article.user-card`; HMR remounts a **new `vnode.state`** (instance identity does not survive, ADR-103) yet the `displayName`-captured selection is recovered; a still-mounted vnode resolved mid-invalidation returns `null` without throwing and the app keeps rendering. Package typecheck clean (`tsc -p tsconfig.json`); full-workspace `pnpm -r typecheck` and `pnpm -r test` green (all 6 spikes + 9 packages unaffected). ADR written at `docs/adr/ADR-106-hmr-mapping-survival.md`; feeds tasks 0013 (`handleHotUpdate`) and 0010 (runtime). Known limitations (see ADR): the HMR round-trip is *simulated* (invalidate→register→remount) with a real-`m.render` app half — the live Vite dev-server edit firing `handleHotUpdate` end-to-end is deferred to 0013 + 0014/0015 (as ADR-105 deferred runtime wiring to 0010); element signatures use `kind`+`tagName` only (no `key`/class yet), so two identical keyless siblings collapse to one signature and an id-lost selection among them degrades to stale rather than guessing.
