## Acceptance Criteria
- Selecting an element shows its owning component and full ancestry chain with resolved display names.
- Clicking an ancestor highlights its DOM range and shows its source; "Open in editor" works per ancestor.
- When multiple source locations exist, an "Open: rendered element / component view / component declaration" choice is offered, defaulting to the most precise (§9.3).
- Exact vs inferred mapping visibly distinguished (§2.4).
- Browser test §19.2.6 (ancestry correct) enabled in the 0015 suite; update 0016's checklist if it recorded an ancestry gap.

## Implementation Notes
- Ancestry comes from `ComponentRecord.parentId` chains (0017); the panel must tolerate hidden components (`markInspectorHidden`) by skipping them.
- Stale-selection behavior per §8.8 applies to ancestry entries too.

Both are wired through `InspectorRuntime` as `componentAncestry`/`componentViewSource` (boundary-guarded, defaulting to `[]`/`null`).

  **A real design correction found while writing the first `ancestryOf` test**: my initial plan had "skip an individually-hidden ancestor but keep walking past it" as the §14 tolerance the Implementation Notes describe. Writing the test for that scenario showed it contradicts 0017's already-shipped, already-tested semantics: `isVisible` treats a hidden ancestor's *entire subtree* as invisible (matching `recordOf`'s existing "excludes a hidden component and its subtree" test), so a descendant of a hidden component is never itself visible in the first place — `resolveDomComponent` already proves this by skipping straight past both to the next visible ancestor. Implemented `ancestryOf` consistently with that (self must pass `isVisible`, which by construction means no ancestor found while walking `parentId` can be hidden either — no per-node hidden check needed in the walk itself) and rewrote the test to assert the correct behavior: a component inside a hidden ancestor's subtree returns `[]` from `ancestryOf`, not a chain with a gap.

  **`packages/overlay`**: `highlight.ts` gained `nodesOfDomRange`/`rectsOfDomRange` (walks a `DomRange`'s `first→last` siblings, reusing the existing `rectsOfNodes`) for highlighting a fragment-root component's full range, not just its first node. `hook.ts`'s `OverlayHook` gained `componentAncestry`/`componentViewSource` (compile-time-asserted against the real `InspectorRuntime` in `hook.test.ts`, per 0012's existing drift guard). `controller.ts` added: `SourceChoice`/`SourceChoiceKind`/`AncestryEntry` types; `computeChoices(record)` — the §9.3 three-way ladder (rendered element via `resolveDomSource` on the record's own `domRange.first` → component view → component declaration), most-precise first, only the ones that actually resolve; `OverlayViewState.ancestry`/`selectedComponentChoices`/`focusedAncestorId`; `focusAncestor(id)` (highlights the ancestor's own DOM range via `rectsOfDomRange`, degrading to the plain selection highlight when the ancestor has no live range) and `revealComponent(id, kind?)` (opens the default or a specific choice, recording a diagnostic instead of throwing when nothing resolves). `focusedAncestorId` resets on every new selection, `clearSelection`, and `promoteStaleSelection` so a stale focus never lingers. `view.ts` replaced the old single-line ancestry placeholder with a real indented, clickable ancestry list (inferred-name and not-mounted markers) and added a "Reveal component" button + conditional "Open: …" choice-button group next to the existing "Open in editor" action, reusing the same controls per ancestry row. `styles.ts` extended the already-present (previously unused) `.mi-ancestry`/`.mi-depth` classes and added `.mi-ancestry-name`/`.mi-ancestry-actions`/`.mi-ancestry-focused`/`.mi-btn-small`/`.mi-reveal-choices`.
