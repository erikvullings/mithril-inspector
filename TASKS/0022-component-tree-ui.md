## Context
REQUIREMENTS.md §9 and §21 Phase 3: expandable component tree in the overlay's Components tab — a Mithril component tree, not a DOM tree — with selection synchronization, search, attrs/state views (via 0020's serializer), fed by batched events (0021).

## Acceptance Criteria
- Tree shows the component hierarchy with display names and keys (e.g. `UserCard key="42"`); plain HTML elements excluded by default, optional expansion of a component into its owned vnode/element tree (§9.1).
- Selection sync (§9.3): DOM pick selects nearest component in the tree; tree selection highlights the DOM range, offers scroll-into-view, shows source/attrs/state, and opens declaration or view source (multi-target "Open:" chooser, most precise default).
- Incremental updates from `RuntimeEvent` batches — no full rebuild per redraw (§9.4); update counters visible per component (§3.2).
- Component search by name; pinned components (§3.2) may be minimal but must not be silently dropped — document if deferred.
- Attrs/state panels use the lazy preview tree: expandable, paginated, getter-on-demand, redacted values shown as `[redacted]`.
- `componentTree.captureAttrs` / `captureState` and `mode: "full"` options respected (§11.1, §17).
- Browser tests: tree renders for the playground, selection sync both directions, keyed reorder keeps tree/DOM association correct.
- Accessibility per §18 applies to the tree (keyboard expand/collapse/navigate, focus indicators).

## Implementation Notes
- Update the Phase-1 placeholder Components tab from 0012.
- Stale/unmounted entries follow §8.8 semantics.
- Performance: virtualize or lazily render large trees; idle CPU near zero (§17).

- 2026-07-18 claude-opus (follow-up): fixed a real bug in this task's own Components-tab subscription, reported by the user after running the actual `apps/playground-vite` playground with `componentTree.enabled`/`mode: "components"` turned on — every component's update-count badge climbed into the thousands within seconds with zero user interaction.

  **Root cause**: `controller.ts`'s `hook.subscribe(...)` listener called `redraw()` on every batched `RuntimeEvent`, and `overlay.ts` wired `redraw` to the *global* `m.redraw()`. Traced against Mithril's own source (`mithril/api/mount-redraw.js`, `mithril/render/render.js`): `m.mount()` registers a root in a shared, module-level `subscriptions` array that `m.redraw()` unconditionally iterates in full — there is no scoped "redraw just this root" API. Since the overlay and the host app resolve to the same `mithril` module, the overlay's own `m.redraw()` call redrew the *entire host app* too. That fired `onupdate` on every one of the app's live components — which the runtime's `wrapped.onupdate` (`components.ts`) bumps unconditionally regardless of whether anything actually changed — producing a fresh `components-updated` batch that the same subscription reacted to by redrawing again. One real app redraw (e.g. its own initial mount) was enough to prime an unbounded, self-sustaining loop needing no further user interaction, entirely because "a redraw happened" was treated as a reason to trigger another global redraw.

  **Fix** (`packages/overlay/src/overlay.ts`, ~20 lines, `controller.ts` untouched): replaced `m.mount(mountPoint, OverlayRoot(controller))` / `redraw: () => m.redraw()` with a manually-invoked `m.render(mountPoint, m(overlayComponent))`. `m.render()` called directly (not through `m.mount`) is scoped to exactly the DOM element passed in — it never registers in Mithril's shared subscription list and never wires the auto-redraw-after-event hook (confirmed in `render.js`: the auto-redraw callback is only set when `m.mount` explicitly passes its own `redraw` as render's third argument). This was safe to swap with no other changes because every state-mutating controller method already calls `redraw()` explicitly at its own end (never relied on Mithril's implicit post-event redraw) — confirmed by grepping every `onclick`/`oninput`/`onkeydown` handler in `view.ts` back to a `controller.*` method. A forward-reference (`let renderOverlay = () => {}`, reassigned once `overlayComponent` exists) avoids a temporal-dead-zone crash in the edge case where `hook.subscribe` delivers a pending `reset` synchronously during controller construction (task 0021).
