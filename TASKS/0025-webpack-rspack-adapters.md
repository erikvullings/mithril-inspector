## Acceptance Criteria

- Plugin injects runtime/overlay entries without requiring app-entry edits; dev-only by default.
- `webpack-dev-server` / Rspack dev-server middleware wires `createInspectorMiddleware` (0011).
- Rspack compatibility verified or divergences documented (§25.9).
- Unit tests for loader transform wiring and middleware registration; one integration fixture per bundler.

## Implementation Notes

- HMR support here is best-effort; document what survives module replacement.

  - **`loader.ts`/`loader.cts`**: the transform logic (`runMithrilInspectorLoader`) is a plain synchronous, framework-agnostic function — directly unit-testable with a fake `LoaderThis`, no real webpack machinery needed. `loader.cts` is the *only* CJS file in the package: webpack/Rspack's `loader-runner` synchronously `require()`s loader files with no async-import fallback, but this package (like every other adapter) is ESM-only (`"type": "module"`). TypeScript's `.cts` extension compiles that one file to CommonJS regardless of the package's own module type; it calls `this.async()` immediately (as loaders must) then reaches the real ESM implementation via a dynamic `import()`, which is unrestricted from CJS. Registered `enforce: "pre"` by the plugin so it always sees the original TS/JSX before ts-loader/babel-loader lower it, and its output map is handed to whichever loader runs next as `inputSourceMap` — how webpack chains loader source maps (AC: "source maps chained correctly with ts-loader/babel-loader configurations").
  - **A genuine bug caught only by a real build, not by documentation-reasoning**: webpack (and Rspack, which follows the same convention) treats any `<scheme>:...`-shaped request — including every other adapter's shared `virtual:mithril-inspector/runtime` specifier from `@mithril-inspector/adapter-kit` — as a URI and rejects it with `UnhandledSchemeError` *before* `resolve.alias` ever runs. Fixed in `virtual-files.ts`: a colon-free `WEBPACK_SAFE_RUNTIME_SPECIFIER` (`"mithril-inspector/virtual-runtime"`) replaces `RUNTIME_MODULE_ID` for this adapter's loader `runtimeModule` option, and the overlay bootstrap's own hardcoded `import "virtual:mithril-inspector/runtime"` line (baked into adapter-kit's `overlayModuleCode()`, not itself modified — ADR-004 bundler-neutrality) is string-rewritten to the safe specifier before being written to disk. Documented prominently in the package README's "Divergences" section and §25.9-style in code comments, not silently patched over.
  - **`virtual-files.ts`**: neither bundler has an in-memory virtual-module hook (Rspack's Rust-side resolver hook can only *redirect* an existing request, confirmed via its own docs), so the runtime/overlay bootstrap source (`runtimeModuleCode`/`overlayModuleCode`, reused verbatim from adapter-kit like every other adapter) is written to real files under the *consuming project's own* `node_modules/.cache/mithril-inspector` — deliberately not `os.tmpdir()` — because standard Node module resolution from that location walks up through the project's own `node_modules`, so the bootstrap's bare `@mithril-inspector/runtime`/`overlay` imports resolve with zero extra `resolveDir`-style configuration (unlike esbuild's adapter, which needed one). `resolve.alias` (plugin.ts) then maps the safe specifiers onto these paths.
  - **`entry.ts`** (`resolveEntryNames`): pure, reads (never mutates) `compiler.options.entry` to find which entry names to target. Deliberately does **not** produce a new entry config to mutate `compiler.options.entry` with — Rspack's own migration docs explicitly forbid mutating `entry` after the compiler is constructed (a breaking change from Rspack 0.x), and the sanctioned replacement — confirmed identical on webpack too — is `EntryPlugin(context, request, name).apply(compiler)` per existing entry name. A dynamic (function) entry can't be auto-injected into; `plugin.ts` logs this via `console.warn` (never silently drops it, §25.9) and the manual-import escape hatch (documented in the README) still works.
  - **`plugin.ts`**: `resolveEntryPluginCtor` reads `compiler.webpack.EntryPlugin` or `compiler.rspack.EntryPlugin` — the back-reference both bundlers expose specifically so plugin authors can reach internal classes without a hard runtime dependency on either package. The plugin's compiled output has **zero runtime import of `webpack` or `@rspack/core`** (only `import type`, erased at build) — both are `peerDependenciesMeta`-optional, so the same `dist/plugin.js` genuinely works for Rspack-only projects with no `webpack` package installed at all. Dev-only guard (§2.1 analog, AC: "production output contains no inspector code"): active only when `enabled` **and** `compiler.options.mode !== "production"` unless `includeInProduction` — both bundlers expose `mode` directly, no watch-mode/minify proxy needed (simpler than Rollup/esbuild's guards). `devServer.setupMiddlewares` wiring (`dev-server.ts`) composes with — never replaces — any existing `setupMiddlewares`, confirmed against Rspack's own dev-server docs to accept the same plain-function middleware shape as webpack-dev-server.
  - **`import.meta.hot` leakage** (Implementation Notes: "verify no leakage in shared code paths"): the shared bootstrap (unmodified, from adapter-kit) does reference `import.meta.hot` for its HMR-invalidation channel; verified via the real webpack/Rspack builds in `tests/integration/` that this is inert, not broken — both bundlers parse `import.meta` natively (any ESM-syntax source is parsed as a Harmony module regardless of output format) and shim it to an object without `.hot`, so the guard safely evaluates false. HMR here is therefore best-effort/inactive by default, as the Implementation Notes anticipated — documented in the README's divergences section rather than silently left unmentioned.
