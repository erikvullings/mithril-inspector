## Context
REQUIREMENTS.md §21 Phase 2: mounted component-instance IDs and parent-child tracking in the runtime, using the mechanism proven in spike 0004. Produces `ComponentRecord`s (§7.3) with stable IDs (§7.2), ownership scopes (§7.5), and `DomRange` links — the data layer for ancestry (0019) and the full tree (0022).

## Acceptance Criteria
- Stable `ComponentId` per mounted instance across redraws; new instance ⇒ new ID; unmount ⇒ record marked unmounted and cleaned (weakly held, §17).
- `ComponentRecord` fields populated: id, parentId, displayName (raw for now — resolution polish in 0018), source, kind (object/closure/class/function/route-resolver/anonymous), mounted, createdAt/updatedAt/updateCount, domRange, childIds. Attrs/state captured as references only — safe serialization arrives in 0020.
- Vnode ownership per §7.5: enter/leave component scope around wrapped views; nested component vnodes start new scopes; no reliance on global-`m` call-stack interception (ADR-005).
- Nearest-component lookup for a DOM node returns correct instance including fragment roots and keyed reorders.
- `mode: "components"` (§17) activates this tracking; `mode: "source"` skips it; overhead in components mode within the <20% median redraw target on the playground (spot-check, not a benchmark suite).
- Runtime unit tests: parent-child ownership, keyed reorder identity, multiple roots, unmount cleanup, route-resolver components.

## Implementation Notes
- Do not claim correctness until keyed redraws, fragments, multiple roots and unmount cleanup are tested (§25.10).
- `markInspectorHidden` (§14) must exclude a component and its subtree from records.
- Update the 0004 ADR if the production implementation deviates from the spike.

  **Two conflicts surfaced during investigation, resolved with the user (via `AskUserQuestion`) before implementation:**
  1. §17 defines `mode: "source"` as "element-to-source mapping only," but the already-tagged `v0.1.0-alpha.1` (task 0016) ships nearest-component lookup and basic ancestry as always-on in the *default* `source` mode, verified by existing tests that never set `mode`. Implementing the gate literally would have silently regressed a shipped, tagged release. **Resolved**: kept `source` mode's shipped behavior for object/closure unconditionally; `mode: "components"`/`"full"` gate only the *new* kinds this task adds (class, route-resolver), which had no earlier alpha behavior to preserve. Verified no regression: full `pnpm -r test` stays green, including `tests/browser`'s mode-implicit assertions.
  2. The task's acceptance criteria wants `kind: "route-resolver"` and a "route-resolver components" unit test, but the transform (§6.5) only detects `view`-shaped components — it has no logic to find `{render, onmatch}` object literals in a real `m.route()` table, and this task doesn't depend on 0009 (transform). **Resolved**: runtime-only — `ComponentRegistry` detects and correctly tracks a `{render}`-shaped definition when given one (via `instrument()`/the public `inspectComponent()` API), unit-tested by driving the registry directly (mimicking `mithril/api/router.js`'s real `RouterRoot.view()` → `currentResolver.render(vnode)` call). Real end-to-end tracking through an app's actual route table remains a follow-up needing transform changes — documented, not silently omitted.

  A third finding, not worth a separate question: bare `function Foo() {...}` **declarations** used as closures are permanently unwrappable from the runtime alone (transform discards `__miComponent`'s return for a declaration binding it can't rebind; no runtime-only heuristic distinguishes a declaration from a `const Foo = () => {}` expression — both can carry a `.name`; global-`m` interception is forbidden, ADR-005). Documented explicitly with a passing test proving the current, honest behavior (`components.test.ts` "function-declaration closures" describe block) rather than left as a silent gap.

  **A real spec-vs-implementation correction found while implementing class components**: ADR-103/105 describe the class mechanism as "a prototype facade... applied to a prototype facade" without pinning down *how*. The first implementation attempt — reassigning `Klass.prototype = Object.create(originalPrototype)`, mirroring the object/closure `Object.create(app)` pattern one level up — **throws** in strict mode: a `class` constructor's `.prototype` property is non-writable (unlike a plain `function`'s). Corrected to snapshot the original `view`/hooks into a plain object first, build the same composed wrapper `composeHooks` already produces for object/closure delegating to that snapshot (avoiding self-recursion), and copy its own properties directly onto the *existing* prototype object as own-property overwrites — more invasive than the object/closure path (mutates an object the app still holds a reference to) but the only mechanism available for a declaration-form binding. `instanceof`/`.constructor` against the original class still hold (only specific methods overwritten, not the prototype chain). Documented in both `packages/runtime/README.md` and a new "Production implementation (task 0017)" section appended to `docs/adr/ADR-103-component-instance-tracking.md`.
