# 0021 Phase 3: batched runtime tree events

Status: done
Priority: medium
Owner: unassigned

Area: runtime
Depends on: 0017

## Context
REQUIREMENTS.md §9.4: the component tree UI must not rebuild on every redraw. The runtime emits batched `RuntimeEvent`s (`components-added` / `components-updated` (patches) / `components-removed` / `dom-associated` / `reset`), coalesced per microtask or animation frame, delivered via `subscribe` on the global hook (§7.1) alongside `getSnapshot()`.

## Acceptance Criteria
- Mount/update/unmount of components produce correct batched events; a redraw touching N components yields one batch, not N notifications (unit-tested with fake timers/rAF).
- `ComponentPatch` carries only changed fields (updateCount, updatedAt, domRange, childIds...) — no full-record spam.
- `getSnapshot()` + subsequent events are consistent (no missed or duplicated records when subscribing mid-stream).
- `reset` emitted on HMR full-invalidation and on multiple-runtime detection (§16).
- Event batching test from §19.1 runtime list passes; overhead stays within §17 targets in `components`/`full` modes.

## Implementation Notes
- Records crossing the event boundary must be serializable-safe (no live DOM nodes in event payloads; DOM lookups stay behind hook methods).
- Subscription returns an unsubscribe function (§7.1); listeners must be exception-isolated (§16).

  **Two ambiguous design points, resolved with the user (via `AskUserQuestion`) before implementing**, since REQUIREMENTS.md §16 gives no operational definition for either and different reasonable designs would produce different public API surfaces:
  1. "reset emitted on HMR full-invalidation" — no existing "invalidate everything at once" concept existed (only per-module `invalidateModule`, which per ADR-106 deliberately does *not* reset; normal per-file HMR already produces correct `components-added`/`components-removed` pairs as instances naturally remount). **Resolved**: added an explicit `InspectorRuntime.resetTracking()` primitive, caller-driven like `invalidateModule`. Wiring an actual Vite call-site (e.g. on a real full-module-graph-invalidation hook) is an explicitly documented follow-up — this task is runtime-only, the same scope boundary task 0017 drew around route-resolver transform detection.
  2. "reset emitted on multiple-runtime detection" — ADR-005 forbids intercepting the global `m`, ruling out detecting duplicate *Mithril.js* instances directly. **Resolved**: fixed `getRuntime()`'s existing (previously silent) protocol-version-mismatch branch — it used to overwrite an incompatible existing hook at `window.__MITHRIL_INSPECTOR__` with no diagnostic; it now logs a `console.warn` (§16) and calls `resetTracking()` on the newly-installed runtime before returning it.

  **A related design problem found while implementing #2**: a `reset` fired via a plain `notify()` call is unobservable if nobody has subscribed yet — which is exactly `getRuntime()`'s situation (the new runtime is returned to the caller *after* creation; nobody can have subscribed before that point). Rather than ship an untestable, silently-dropped event, `resetTracking()`/the shared `emitReset()` helper (also now used by the pre-existing §16 error-boundary `onDisable` path, previously a bare `notify()`) delivers immediately if `subscribers.size > 0`, otherwise sets a `pendingReset` flag that `subscribe()` checks and delivers (once, exception-isolated via the same `boundary.guard` `notify()` uses) to the very next listener — unit-tested directly (`runtime.test.ts` "defers reset delivery to the first subscriber..." / "does not redeliver a pending reset to a second, later subscriber").

  **A real orphaning bug found and fixed while building `resetTracking()`**: `components.ts`'s `byState` is a `WeakMap` (can't be `.clear()`'d), so an initial `reset()` that only cleared `byId`/`roots` left a still-mounted instance's *own* `byState` entry pointing at its old (now off-`byId`) record — its next redraw would find that stale entry via `byState.get(state)` and conclude it was "still tracked," never reallocating, permanently orphaning it outside `byId`/`roots` (invisible to `getSnapshot()`/`resolveDomComponent`/etc. forever, not just until its next redraw). Caught by a test I wrote expecting the opposite (`runtime.test.ts` "orphaned instances still mounted across a reset reappear once their view next runs"). Fixed with a registry-local `epoch` counter: every `InstanceRecord` stamps the epoch it was allocated in; `reset()` bumps the epoch; a `liveRecordOf()` helper (replacing raw `byState.get` at every call site that decides "reuse vs. reallocate" — `composeHooks`' wrapped `view`, `composeRouteResolver`'s `render`, `cleanup`, `idOf`, and `visitForOwnership`'s flush-time tree walk) treats a stale-epoch entry as untracked, so the instance is transparently reallocated (fresh `ComponentId`, reported via `components-added`) the next time it actually renders. `touch()` (called from `oncreate`/`onupdate`) needed no change — Mithril always runs `view()` before those hooks, so by the time they read `byState`, `view()` has already refreshed it if needed.
